Projects

There will be five projects over the course of the semester, each contributing 10% to your final grade, for a total of 50%. You must work on all of the projects individually, though you may collaborate on idea, algorithms, and debugging as long as you don’t share large chunks of code.

Handing in: All projects will be handed in through a git repository that will be assigned to you; the specific details will be announced on Piazza. Each project will have its own repository, with both the student and instructors as members. The project must have a Makefile to manage compilation; the initial project skeleton that you are provided will have a working Makefile that will typically require minimal modification (if any) to customize for your project. As you are working on a project you must regularly commit files to demonstrate activity and push the results to provide instructors access. Only code that is pushed will be considered “turned in”, with the date stamp of the push, not the individual commits.

Due dates: Each project will be worked on for approximately a 3 week period. A check in (to force you to start early) will be due after two weeks, and the main project will be due on the date indicated (by midnight). If students notify the instructors (on Piazza) in advance, they will be allowed to turn in projects up to five days late; extensions should be used rarely as each project builds on previous concepts, so if you are late on one project we do not want it to cascade into the next. Instructors may talk with students who use multiple extensions to help you come up with a better time management plan.

Once the five-day late period has passed, project solutions will be handed out to the class. As such, no project submissions can be accepted beyond that point, since the solutions are then publicly available. Plan accordingly: an extension buys you five days, not an open-ended window.

Check-Ins Project check-ins will be due exactly one week before the main project is due. They require you to have started implementing the project features (you are welcome to start with the easy ones first!) Specifically, check-ins are worth 25% of the score of the overall project (i.e., 2.5 points) and require you to:

  • Successfully pass at least 25% of the functionality test cases for the project. (You don’t need to worry about the error test cases yet.) For Projects 3–5, use the designated current-project check-in group described in the handout and selected by make check-in; inherited regression tests do not replace that milestone.
  • Include an initial README file indicating which test cases you pass.
  • Add a my_tests/ directory with at least one test program in it, somehow different from the instructor provided test cases. Your code does not need to pass this test case yet, but it must adhere to the project specifications. Particularly clever test cases (especially those that help other students find flaws in their code) may earn you extra credit.

Note regarding student-supplied test cases: We will NOT automatically take points off the code of other students who fail your test case unless it uncovers a problem that they should have reasonably caught. We WILL, however, let them know about the problem know so that they can avoid the same problem in the future. Our goal is for everyone to learn how to produce as solid compilers as possible, not to nickle-and-dime for points.

Quizzes

There will be five quizzes in this course, each of which will be worth 10% of your final grade, for a total of 50%. Note that you must score at least 50% of the total quiz points or you will automatically receive a zero in the course. Each quiz is tied to the project you are working on at the time, and each one is offered in three versions. All of the dates are on the course calendar.

  • The first version comes in the middle of the three-week period you spend on the associated project, once you have had time to make yourself familiar with the concepts. Beyond testing you, it is meant to highlight the key points and the issues you are most likely to run into over the rest of the project.
  • The second version comes a few days before that project is due, when you have used all of the material in practice and should be considerably more comfortable with it.
  • The third version is given during the final exam slot, in place of a normal final. At that point you may retry any of the quizzes you would like to improve.

Each version is a new quiz covering the same material, and only the highest-scoring attempt for each quiz will be used in calculating your final grade. A quiz that you are already happy with is one you never need to take again.

Quiz logistics: All quizzes are administered through D2L, but they are taken in person, during our regularly scheduled class session. You must be present in class to take a quiz. Bring a laptop on quiz days. If your machine dies or you otherwise end up without one, don’t panic — I bring a few paper copies of each quiz to class for exactly that situation.

Make-ups: There are no make-up quizzes. The three scheduled attempts at each quiz are the make-up mechanism — if you miss the first attempt, take the second; if you miss both, take the third during the final exam slot. If you miss all three attempts at a given quiz, you will receive a zero for that quiz.

Project-specific questions: Quizzes will include questions about the projects — not just the concepts behind them, but the specific decisions, trade-offs, and failure modes you run into while building the thing. These questions are written so that a student who did the work can answer them quickly, and a student who did not cannot answer them at all, no matter how well they have read the project description. This is deliberate, and it is the main reason the projects and the quizzes are each worth half of your grade: the projects are how you learn the material, and the quizzes are how I find out whether you did. I also reserve the right to ask questions about what you specifically did in your own code. Since a project has to be handed in before I can ask you about it, questions of that kind will always show up on a later quiz than the project they refer to.

Software and Tools

You will develop your projects on your own machine, so you need a working toolchain in place before the first project is due:

  • Standard developer tools, including make and git.
  • Tools for working with WebAssembly (we will cover the specific options in class before they are needed, starting with Project 3).

You will also need an account on whichever repository host we use for handing in projects; that will be announced on Piazza.

Getting a compiler installed and actually working is often the most frustrating part of the first week of a course like this, and the answer differs across Windows, macOS, and Linux. This class is small enough that I am willing to work with you individually until your setup genuinely works — come to office hours or post on Piazza, and we will get it sorted out. Please do not quietly fight a broken toolchain for two weeks; you cannot do the projects without one, and this is a solvable problem.

Grading Policies

Beyond the grade you receive on your projects and quizzes, several other factors can affect your final grade:

Extra Credit: Throughout the course, you may have opportunities to receive extra credit points by implementing difficult additional features, and in general I may reward particularly clever answers with extra credit points. Extra credit is not required, and I will construct any grade curve ignoring extra-credit points. Once grades are assigned, I will consider the extra credit to boost grades up to a maximum of one step (that is, one-half letter grade).

Re-grades: Requests for re-grading can go in either direction. I am often generous when I first grade something, so please be sure that I did make a mistake before you submit your request. On the other hand, my goal is for you to understand the course material, so I will always be willing to explain to you any portion that you are stuck on. All requests for re-grades must come in writing, within one week of the return of the graded item. Thereafter, no requests will be considered, so be sure to look over your returned projects and quizzes in a timely manner.

Academic Dishonesty: Because a goal of this course is to teach professionalism, any academic dishonesty will be viewed as evidence that this goal has not been achieved, and will be grounds for receiving a final grade of 0.0. Examples of academic dishonesty include (but are not limited to):

  • Copying another student’s code or exam answers
  • Using code implemented by someone else specifically to solve this project (i.e., don’t get someone else to do your project for you!)
  • Using code implemented by someone (or something) else without attributing credit (i.e., you can use tools, libraries, code snippets from the web, or even LLMs, but you must include a comment in your code or your README!)
  • Including code as your own that you do not understand.
  • Writing code that deceptively passes the test cases, but doesn’t solve the problem given (i.e., do not abuse automatic grading mechanisms to gain unearned points.)
  • Submitting a solution that you do not understand or cannot explain to an instructor.
  • Providing false information to the instructor about matters related to the course.
  • Facilitating another student in any of these activities.

You must be able to explain how your code works if requested by the instructor. It is understood that you may not understand every nuance of the code, but do not use any code in your projects if you don’t think you have a general understanding of why it produces the result it does.

Beyond the course-level consequences described above, MSU requires instructors to report academic dishonesty to the student’s academic dean; such reports become part of your student record and may carry additional university-level consequences. The relevant university policies are MSU’s Integrity of Scholarship and Grades policy and General Student Regulation 1.00.

Generative AI

Large language models and AI coding assistants are a real part of modern software development, and I am not going to pretend otherwise. You may use them on the projects, subject to three rules:

  1. Attribute it. Any code that came from an LLM — like code from a library, a web search, or another person — must be credited in a comment in your code or in your README. The standard here is exactly the same as for any other outside source.
  2. Understand it. You must be able to explain how any part of your submission works if an instructor asks. Submitting code that you cannot explain is academic dishonesty regardless of where it came from, and “the AI wrote it” is not a defense.
  3. Remember what it is for. The projects exist to teach you how compilers work; the quizzes test whether you learned it. Quizzes include questions that can only be answered by someone who actually built the project (see the Quizzes section above), so if you outsource the thinking on a project, you will typically discover the cost two weeks later on the corresponding quiz, when there is no assistant available and half your grade is on the line.

A practical warning: a compiler is a large, stateful program where a subtly wrong decision in one phase surfaces as a baffling failure three phases later. AI assistants are good at producing plausible code for problems like this and much less good at producing correct code for them. However the code got written, the bugs are yours to find and explain.

Quizzes are different. Quizzes are closed to all outside assistance, including AI tools, notes, and other people, unless I explicitly say otherwise for a particular quiz.

Oral exams: If I have reason to believe that a student has outsourced their learning — to an AI assistant, to another student, or to anything else — I reserve the right to ask that student to explain their project to me in person, and to use that conversation in determining their grade on the project. This is not a punishment and it is not an accusation; it is simply the most direct way to find out what someone actually knows. If you did the work, an oral exam is a short and fairly pleasant conversation about code you understand.
