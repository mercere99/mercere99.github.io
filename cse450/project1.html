Marquee Specifications

A program in Marquee is a script for a sign: it builds up strings, stores them, and posts them to the sign at specified times. A program consists of keywords (commands), variable names, literal strings, and numbers, as well as whitespace and comments. Each line has a single keyword; the keywords are followed by zero or more arguments, which can be variable names, literal strings, or numbers. Arguments may be separated by any number of spaces or tabs.

  • The keywords are “LOAD”, “SAVE”, “JOIN”, “CUT”, “REPEAT”, “WAIT”, and “SHOW”. These are reserved values and cannot be used as variable names.
  • The variable names are sequences of alphanumeric characters and underscores. A variable name cannot begin with a digit. For example, state, i, or my_var4, but not 4ever.
  • The literal strings are sequences that begin and end with either a single quote or double quote (start and end symbols must be identical.) A literal string may not have a quote inside of it of the same type as the start/end quote, unless you are doing the second extra credit.
  • The numbers come in four flavors (integer, hexadecimal, decimal, and duration), described in detail below.
  • The comments come in two flavors (line comments and block comments), also described below.

The internal state of a Marquee program consists of:

  • a global stack of strings,
  • a table of variable names mapped to their current values (i.e., a “symbol table”), and
  • a clock, measured in whole milliseconds, which starts at 0.

Numbers

Marquee has four kinds of numeric literal. Getting these right is the central challenge of the project.

Kind Examples Rules Value as text
Integer 42, 7, 1_000_000 One or more decimal digits. Single underscores are allowed between digits as separators. The digits, with underscores removed (1_000_000 → 1000000)
Hexadecimal 0x2A, 0xff, 0xDEAD_BEEF A 0x prefix (lowercase x) followed by one or more hex digits (0-9, a-f, A-F). Underscores are allowed between hex digits. The decimal value (0x2A → 42, 0xff → 255)
Decimal 3.5, 0.25, 1_000.50 Digits, a single period, then more digits. At least one digit is required on each side of the period. Underscores are allowed between digits on either side. As written, with underscores removed (1_000.50 → 1000.50)
Duration 250ms, 1.5s, 2m, 90_000ms An integer or a decimal immediately followed by a unit: ms (milliseconds), s (seconds), or m (minutes). No whitespace is allowed before the unit. The total number of whole milliseconds (1.5s → 1500, 2m → 120000)

A separator underscore must have a digit on both sides of it; 1_000 is a legal integer, but _100, 100_, and 1__000 are not. If a duration works out to a fraction of a millisecond, round down to the nearest whole millisecond (so 0.0005s is a duration of 0 milliseconds).

Some of these token types are prefixes of others, and Marquee relies on the standard lexer rule that the longest match wins. The following table shows how several tricky inputs must be tokenized; your lexer should reproduce all of them.

Input Tokenizes as Why
1_000 one integer Longest match takes the whole thing, rather than an integer 1 followed by a variable named _000.
1_ integer 1, then variable _ The trailing underscore cannot be part of the number, so the longest legal integer is just 1.
0x1F one hexadecimal Not an integer 0 followed by a variable named x1F.
0x integer 0, then variable x A hex literal needs at least one hex digit after the prefix.
250ms one duration Not an integer 250 followed by a variable named ms.
250 ms integer 250, then variable ms Whitespace is not allowed before the unit.
12msec duration 12ms, then variable ec Longest match takes 12ms as a duration; the leftovers are a perfectly good variable name. (This will end up as an error when the statement is processed, but that is the parser’s problem, not the lexer’s.)
3. integer 3, then a stray . A decimal needs digits after the period, so 3 is the longest number here and the . is not part of any legal token.
.5 a stray ., then integer 5 Likewise, a decimal needs digits before the period.

Any character that cannot begin a legal token (such as the stray . above, or a @) should be reported as an Unexpected token error, with the offending character as the lexeme. It is easiest to handle this by giving your lexer a final catch-all pattern that matches any single character, so that it always produces a token rather than failing. The two exceptions are a quote that never closes and a /* that never closes; those have their own error messages, described under Error Reporting.

Comments

Marquee has two kinds of comment, and both must be removed before the tokens are processed.

  • A line comment is a pair of forward slashes (that is, “//”) followed by any sequence of characters, ending at the next newline.
  • A block comment begins with “/*” and ends at the next “*/”. A block comment may span multiple lines, and it may appear in the middle of a line. Block comments do not nest: the first */ ends the comment, so in /* outer /* inner */ the comment is over after the only */ that appears.

Neither kind of comment has any special meaning inside of a literal string. For example, SHOW "https://cse.msu.edu" prints the whole URL, and SHOW "/* hello */" prints /* hello */ exactly.

A /* with no matching */ before the end of the file is an error (see Error Reporting).

Lines and Statements

Every statement must be contained on a single line: the keyword and all of its arguments appear together, and the statement ends at the newline. Empty lines, and lines that contain only whitespace and comments, are allowed and do nothing.

A block comment that spans multiple lines also ends the statement it appears in. For example:

SHOW /* this comment
ends the statement */ "hello"

Here the SHOW is a complete statement with no arguments, and "hello" begins a new statement (which will report an Unknown command error, since a literal string is not a keyword).

The LOAD and SAVE Keywords

The LOAD and SAVE keywords allow a Marquee programmer to control the top of the stack and the values associated with variables stored in the symbol table.

A LOAD statement begins with the keyword LOAD followed by a single argument that is a variable name, a literal string, or a number. If a variable name is used, the value of that variable is pushed onto the stack. If a literal string is used, the string it directly represents is pushed onto the top of the stack. If a number is used, its value as text (per the table above) is pushed onto the top of the stack.

A SAVE statement begins with the keyword SAVE followed by a single variable name. The top string on the stack is removed and placed into that variable as its new value.

For example:

Code Stack (TOP →) Symbol Table Notes
LOAD "FIRST" “FIRST” (empty) LOAD a literal string onto stack
LOAD "next" “FIRST”, “next” (empty) Most recent string is at stack top
SAVE var1 “FIRST” var1=“next” SAVE sets variables in symbol table
LOAD 'March' “FIRST”, “March” var1=“next”
LOAD 0x04 “FIRST”, “March”, “4” var1=“next” Numbers are loaded as their text value
SAVE day “FIRST”, “March” var1=“next”, day=“4”
SAVE month “FIRST” var1=“next”, day=“4”, month=“March”
LOAD day “FIRST”, “4” var1=“next”, day=“4”, month=“March” LOAD can be called on a variable

The JOIN and CUT Keywords

The JOIN and CUT keywords are used to either merge two strings together (appending one to the other) or to split a single string apart into two pieces.

A JOIN statement begins with the keyword JOIN followed by one or two optional arguments, each of which is a variable name, a literal string, or a number. If one or both arguments are missing, values from the top of the stack will be used in their place. The strings associated with the two arguments should be merged together into a single string and that resulting string should be pushed onto the top of the stack.

For example: JOIN "CSE" "450" will push the string “CSE450” onto the stack.

A CUT statement begins with the keyword CUT, followed by one or two arguments, the delimiter and the pattern (the second of which is optional). The command will search for the delimiter inside of the pattern, and then split the two pieces from either side (removing the delimiter from it entirely). The resulting sub-strings are pushed onto the stack in order. For example, if the command is:

CUT "at" "Foundation"

it would find the “at” in the middle of “Foundation”, removing it and splitting the string apart at that point. It would then push the strings “Found” and “ion” onto the top of the stack. Since “Found” is pushed first, it will be below “ion” on the stack.

If the delimiter is not found anywhere inside of the pattern, the entire pattern is pushed onto the stack first, followed by an empty string.

Arguments that are provided always fill in from the left, so the single argument of a CUT is always the delimiter. Any argument that is missing is taken from the stack, from right to left; that is, when both arguments of a JOIN are missing, the first value popped becomes the second (right) argument and the next value popped becomes the first (left) argument. A CUT with no delimiter is a Missing argument error; JOIN and SHOW are the only commands that may appear with no arguments at all. For example:

Code Stack (TOP →) Notes
LOAD "This is a " “This is a” Load beginning onto stack
LOAD "sentence" “This is a”, “sentence” Load rest onto stack
JOIN “This is a sentence” No arguments, so top two strings on stack are merged
CUT ” ” “This”, “is a sentence” Only one argument (a single space), so the pattern was taken from stack
CUT ” ” “This”, “is”, “a sentence”
CUT ” ” “This”, “is”, “a”, “sentence”
JOIN ” new ” “This”, “is”, “a”, ” new sentence” JOIN with one argument will pre-pend to top of stack
JOIN “This”, “is”, “a new sentence”

The REPEAT Keyword

A REPEAT statement begins with the keyword REPEAT, followed by a count and then an optional argument. The count must be an integer or a hexadecimal number; a decimal or a duration is an error. If the second argument is missing, the string is taken from the top of the stack. The string is repeated count times and the result is pushed onto the stack. A count of 0 produces an empty string.

Code Stack (TOP →) Notes
LOAD "-" “-”
REPEAT 5 “—–” No second argument, so the top of the stack is used
REPEAT 3 "ab" “—–”, “ababab”
REPEAT 0x2 "!" “—–”, “ababab”, “!!” A count may be written in hex

The WAIT and SHOW Keywords

A WAIT statement begins with the keyword WAIT followed by a single duration, which is added to the program’s clock. Nothing is printed, and the stack is not changed. Your interpreter must not actually pause; the clock is a number that you keep track of, not real elapsed time. An argument that is not a duration is an error.

A SHOW statement begins with the SHOW keyword, followed by zero or more arguments. If at least one argument is provided, the strings associated with each argument should be printed to the screen. If no argument is provided, the top of the stack is popped and printed to the screen.

Every line printed by SHOW begins with the current clock value in square brackets, followed by a single space, and ends with a newline. Beyond that prefix, no additional whitespace should be added. So a SHOW at the very beginning of a program prints [0] before its text.

Here are some example statements (assume that they follow the sample code above):

Code Stack (TOP →) Symbol Table Output
SHOW "Hello" “This”, “is”, “a new sentence” [0] Hello
WAIT 1.5s (unchanged) (none)
SHOW “This”, “is” [1500] a new sentence
WAIT 500ms (unchanged) (none)
SAVE my_word “This” my_word=“is” (none)
SHOW 'This ' my_word ' is printed.' “This” my_word=“is” [2000] This is printed.

A Complete Example

// Sign script for the CSE 450 classroom
LOAD "="
REPEAT 12
SAVE rule           // rule is now a line of 12 equals signs

LOAD "CSE"
LOAD "450"
JOIN
SAVE course         /* course is now "CSE450" */

SHOW rule
SHOW course " -- Compilers"
WAIT 1.5s

This code should output:

    [0] ============
    [0] CSE450 -- Compilers
    [1500] ============

Error Reporting

In addition to being able to load in and interpret a working Marquee program, you also need to be able to identify incorrect code and report back to the user what the problems were.

All errors must begin with “ERROR (line ??):” with the ?? being replaced by the actual line number that the error occurred on. For example:

ERROR (line 3): Unknown variable 'foo'

The specific errors that your program must report are:

Error Trigger
Unknown command ‘ABC’ If the first non-whitespace token of a statement is not a keyword. Note that empty lines (consisting only of whitespace or comments) ARE allowed.
Unknown variable ‘ABC’ If an argument is a variable name, but not already in the symbol table
Stack underflow If a command tries to pop a string from an empty stack
Missing argument If a command is missing an argument that it requires
Unexpected token ‘ABC’ Any other time an invalid token appears (such as too many arguments, a keyword as an argument, a duration where a count is required, a count where a duration is required, or a character that cannot start any legal token.)
Non-terminating string literal If the input file has a string with an open quote, but no close to match it on the same line.
Non-terminating comment If the input file has a /* with no matching */ before the end of the file.

In all cases above, the ‘ABC’ should be replaced with the actual lexeme that was found. For a non-terminating comment, report the line on which the /* appeared. Multiple test cases exist associated with each error to help you refine your output.

Once an error occurs, you should halt execution. DO NOT try to recover and continue interpreting the code from there.

Implementation Suggestions

Token Identification

In implementing the Marquee language, you should first design the regular expressions that you need to identify the relevant tokens and then use Emplex to build a C++ lexer that will identify them. Specifically, you should consider identifying the keywords either as a single KEYWORD token type (where you then check the lexeme produced) or as seven different token types, one per keyword (which will allow you to use a switch statement to act on a given keyword). You also need to identify variable names, literal strings, and each of the four kinds of number, as well as eliminate whitespace and both kinds of comment.

A pattern is a rule by which a token is identified. It will be up to you as part of this project to design a regular expression that describes the patterns associated with each token type that you need. A lexeme is an instance of a pattern that was matched in a source file. For example, “my_var” is a lexeme that might be categorized as the token type IDENTIFIER. On the other hand the lexeme “   ” is a lexeme of three spaces that might get identified as a token of the type WHITESPACE.

When multiple patterns match the text being processed, a lexer will choose the one that produces the longest lexeme that starts at the current position. If two different patterns match lexemes of the same length, a lexer will choose the one that comes first in the provided list. For example, in a C++ compiler if we had the lexeme “int” it could be matched either as a TYPE or as an IDENTIFIER. As long as TYPE type comes first in the token patterns, it will be correctly classified. If, however, we had the variable name “interest_rate”, we don’t want the lexer to stop after the “int” at the beginning and select “TYPE”; it will instead find the longer match of IDENTIFIER.

A few specific things to think about as you design your patterns:

  • Do the numbers first, and test them by themselves. The four numeric types overlap each other and overlap variable names; the table of tricky inputs in the specification above is there so that you can check your patterns before the rest of your code exists.
  • You cannot look ahead. Emplex has no way to say “match this only if that follows” and no way to refer back to an earlier part of a match. Every rule in the specification has to be built into the pattern itself. In particular, this means the unit on a duration is part of the duration pattern, and the two styles of literal string need to be handled as two alternatives rather than as one pattern that remembers which quote it started with.
  • Separators are a “between” rule, not a “contains” rule. A pattern like “digits and underscores in any order” will happily match 1__0 and 100_. Think about the shape of a number as a first digit group followed by repeated (separator + digit group) pieces.
  • Block comments are the hardest pattern here. You need to match everything up to the first */, which means being careful about how you handle a * that is not followed by a /. Build it up slowly and test it on /**/, /***/, /* a * b */, and a comment that spans three lines.
  • Order matters. Keywords need to come before variable names in your list, or SHOW will lex as a variable name.
  • You can detect the two “never closes” errors with the longest-match rule itself. Consider what happens if, after your pattern for a complete literal string, you add a second pattern that matches just a single quote character. When a string is properly closed, the complete-string pattern produces a longer lexeme and wins; when it is not, only the short pattern can match, and you have a token that means “a quote started here and nothing legal followed.” The same idea works for an unterminated block comment. This is a standard trick for reporting lexical errors with a useful line number, and it is worth understanding rather than special-casing in your interpreter.

Emplex’s built-in help lists every regular expression feature it supports, including character classes, ranges, negation, and the {n}, {n,}, and {m,n} repetition operators. It is worth reading before you start.

C++ Implementations

As you implement the internal state of the interpreter, you will need to consider how you implement some internal classes:

Each string can be implemented directly as an std::string. (Note that std::string is just an alias for std::basic_string<char>).

The stack can most directly be implemented as an std::stack of strings, though std::vector is also a good choice.

The symbol table will get much more complex in future projects (where you will need to worry about scopes, variable types, and more useful errors that indicate where variables were first defined), but for now you should be able to use just a std::map or std::unordered_map of variable names to current values (i.e., a map of std::string to std::string.) Remember, in C++, maps will automatically insert entries if you try to index in and the key doesn’t already exist. You can use the contains() member function to first check if it exists.

The clock is just an integer count of milliseconds; a size_t is fine.

Converting a numeric lexeme to its text value is a small amount of string work once the lexer has done its job. Strip out any underscores first (see std::erase), then convert as needed — std::stoull takes a base as its third argument, so a hex lexeme (with the 0x still attached) converts with a base of 16.

Remember also that when you read in a token of type “string literal”, you need to remove the quotes to convert it to an internal string. If you are doing the escape characters extra credit (see below) you may have to do additional processing of the string.

We highly recommend that you modularize your code as much as possible. If you find yourself doing the same task multiple times, turn it into a function. For example:

  • A helper function to trigger errors (where you send it the line number and main message) will also make it easier to standardize that output format, plus it can exit for you after an error.
  • Helper functions to push and pop the stack can, for example, check if the stack is empty before popping and report the appropriate error if it is.
  • A helper function to get the current value of a variable can first ensure that variable exists (and throw an error if not.)
  • A helper function to resolve an argument token into a string (handling literals, variables, and numbers in one place) will be used by almost every command.
