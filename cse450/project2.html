Running a Marquee+ Program

Your executable should take a single Marquee+ source file on the command line:

./Project2 example.marquee

Parse the complete program before executing any of it. If the program contains a lexical, syntax, or semantic error, report the first error and produce no normal program output.

Marquee+ retains the program clock from Project 1. It begins at 0 milliseconds, WAIT advances it, and SHOW prints its current value. The stack and the LOAD, SAVE, JOIN, CUT, and REPEAT commands from Project 1 are no longer part of the language.

Unless this handout says otherwise, all Project 1 lexical rules still apply. This includes identifiers, string literals, integer/hexadecimal/decimal/duration literals, whitespace, line and block comments, literal normalization, and lexical error handling.

Values and Truth

Marquee+ does not have a type system. Every runtime value is a string.

  • The empty string ("") is false.
  • Every nonempty string is true.
  • Boolean operators produce "1" for true and "" for false.

This rule is intentionally based on strings, not numbers. In particular, the numeric literal 0 is converted to the string "0", so it is true. There is no numeric arithmetic in Marquee+.

Statements

Marquee+ supports the following statements:

SHOW expression
WAIT duration
VAR identifier = expression
IF (expression) statement
IF (expression) statement ELSE statement
WHILE (expression) statement
{ statements }
expression

An expression used as a statement is evaluated and its result is discarded. This is particularly useful for assignments.

Simple statements end at a newline or immediately before a closing brace. A source line may contain at most one simple statement. Empty lines and comments may appear between statements. As in Project 1, a newline inside a block comment still separates statements.

A useful grammar for the statement structure is:

program          -> NEWLINE* (statement NEWLINE*)* EOF
statement        -> show_statement
                  | wait_statement
                  | var_declaration
                  | if_statement
                  | while_statement
                  | block
                  | expression
show_statement   -> "SHOW" expression
wait_statement   -> "WAIT" DURATION
var_declaration  -> "VAR" ID "=" expression
if_statement     -> "IF" "(" expression ")" statement
                    (NEWLINE* "ELSE" statement)?
while_statement  -> "WHILE" "(" expression ")" statement
block            -> "{" NEWLINE* (statement NEWLINE*)* "}"

This grammar omits statement terminators for readability. Your parser must still enforce the line-boundary rules described above.

SHOW

SHOW evaluates exactly one expression and prints its value, preceded by the program clock:

SHOW "Hello, " + "world!"
[0] Hello, world!

Use the + operator when you want to combine multiple values into one output.

WAIT

WAIT takes one duration literal and advances the clock. It should not delay the actual execution of your interpreter.

WAIT 1.5s
SHOW "Done"
[1500] Done

Unlike SHOW, WAIT does not accept a general expression.

Variables and VAR

Declare a variable with VAR:

VAR greeting = "Hello"
SHOW greeting

Each program has an implicit global scope. A braced block creates a nested scope. A variable is visible after its declaration and throughout nested scopes, but not after its declaring scope closes. An inner declaration may shadow a variable from an outer scope. Declaring the same name twice in one scope is an error.

VAR message = "outside"
{
  VAR message = "inside"
  SHOW message
}
SHOW message
[0] inside
[0] outside

Declarations are registered while the program is parsed. Each variable’s storage begins as the empty string. Executing its VAR statement evaluates the initializer and stores the result. Consequently, a declaration skipped by control flow retains the empty string. If a declaration is inside a loop, its initializer runs each time execution reaches it.

Only braces create a new lexical scope; an unbraced IF or WHILE body does not. Using braces for declarations inside control-flow statements is strongly recommended.

IF and ELSE

IF executes its body when its condition is nonempty. An optional ELSE body executes otherwise.

IF (name == "Ada") {
  SHOW "Welcome back!"
}
ELSE {
  SHOW "Hello, " + name
}

The body after IF or ELSE may be any statement. Therefore ELSE IF works without any special syntax or AST node:

IF (answer == "yes") SHOW "accepted"
ELSE IF (answer == "no") SHOW "rejected"
ELSE SHOW "unknown"

An ELSE belongs to the nearest preceding unmatched IF.

WHILE

WHILE repeatedly evaluates its condition and executes its body as long as the condition is nonempty.

VAR remaining = "xxx"
WHILE (remaining) {
  SHOW remaining
  remaining = remaining - "x"
}

Marquee+ has no BREAK or CONTINUE statement; those will be introduced in Project 3.

Expressions

Expression terminals are identifiers, string literals, all numeric/duration literals from Project 1, and parenthesized expressions. Literal values are normalized exactly as in Project 1, and their normalized text becomes their runtime string value.

The unary ! operator negates truth: it produces "1" when its operand is empty and "" otherwise. It may be applied repeatedly, as in !!value.

The binary operators are listed below. Precedence 1 binds most tightly.

Precedence Operators Associativity Meaning
1 /, % Left Trim after or through the first matching substring
2 +, - Left Concatenate; remove the first matching substring
3 ==, !=, <, <=, >, >=, CONTAINS Non-associative Compare strings; test containment
4 = Right Assign to a variable

Unary ! binds more tightly than every binary operator. Parentheses may be used to override precedence.

The / operator keeps the portion of its left operand before the first match of its right operand. If no match exists, it returns the original left operand. The % operator keeps the portion after the first match; if there is no match, it returns the empty string:

"Testing" / "i"    // "Test"
"Testing" % "i"    // "ng"

The - operator removes only the first occurrence of its right operand. If the right operand is not found, the left operand is unchanged. For example:

SHOW "One" + "Two" + "Three" - "w"

prints:

[0] OneToThree

Comparisons are case-sensitive and use ordinary lexicographic string ordering. CONTAINS produces "1" when the right string occurs within the left string, and "" otherwise.

The left side of = must be a plain variable reference. Assignment stores and returns the assigned value, so chained assignment works:

a = b = "shared"

Comparison operators are non-associative. An expression such as a < b < c is an error; use separate comparisons instead.

One possible recursive-descent grammar is:

expression     -> assignment
assignment     -> comparison ("=" assignment)?
comparison     -> join (comparison_op join)?
join           -> trim (("+" | "-") trim)*
trim           -> unary (("/" | "%") unary)*
unary          -> "!" unary | primary
primary        -> ID
                | LIT_STRING
                | INTEGER
                | HEX
                | DECIMAL
                | DURATION
                | "(" expression ")"
comparison_op  -> "==" | "!=" | "<" | "<=" | ">" | ">=" | "CONTAINS"

This grammar accepts a non-variable on the left side of =; detect that case and report an illegal-assignment error.

Complete Example

VAR course = "CSE" + 450
VAR remaining = "xxx"

SHOW course + " -- Compilers"
WHILE (remaining) {
  WAIT 250ms
  SHOW remaining
  remaining = remaining - "x"
}

IF (course CONTAINS "450") {
  SHOW "ready"
}
ELSE {
  SHOW "error"
}

[250] xxx
[500] xx
[750] x
[750] ready

Abstract Syntax Tree

After lexing, parse the complete program into an AST. Do not execute statements directly from the parser. Each AST node should represent one language construct and provide the behavior needed to execute or evaluate that construct.

Reasonable node categories include:

  • literal and variable-reference expressions;
  • unary and binary expressions;
  • assignment expressions;
  • variable declarations;
  • SHOW and WAIT statements;
  • blocks, conditionals, and loops; and
  • a program root.

You do not need to use these exact class names or inheritance structure. Aim for a design in which parsing, name resolution, and execution have clear responsibilities.

Symbol Table and Scope

Build a scoped symbol table while parsing. A straightforward design uses:

  • a vector containing one storage record for each declared variable; and
  • a stack of maps from variable names to entries in that vector.

Push a map when entering a braced block and pop it when leaving. Look up a name from the innermost scope outward. AST variable nodes should retain a stable ID, index, or pointer to the resolved storage record rather than repeating a string lookup every time they execute.

Because the whole file is parsed before execution, parsing is also when you should detect unknown variables, same-scope redeclarations, and invalid assignment targets.

Lexer Updates

Begin with your Project 1 lexer. Preserve its rules for strings, numeric and duration literals, comments, newlines, and lexical errors. Then:

  • keep SHOW and WAIT as keywords;
  • add VAR, IF, ELSE, WHILE, and CONTAINS;
  • add tokens for every operator and delimiter used by Marquee+; and
  • remove keyword rules for the retired Project 1 commands.

Be sure that ==, !=, <=, and >= are recognized as single tokens. If your lexer ends with a catch-all unexpected-character rule, punctuation will not be returned automatically; add explicit rules for (, ), {, }, /, %, +, -, =, and ! as well. Put comment rules in place so that // and /* ... */ are not mistaken for division.

Errors

Stop after the first error and return a nonzero exit status. Include the source line number and a useful message. At minimum, handle:

  • every lexical error required in Project 1;
  • an unexpected token or missing statement component;
  • a missing closing parenthesis or brace (include the opening line when useful);
  • use of an unknown variable;
  • redeclaration of a variable in the same scope;
  • an illegal assignment target; and
  • chained use of a non-associative comparison operator.

Exact wording is not required unless a supplied test specifies it, but the message must clearly identify the problem. Errors go to standard error; normal SHOW output goes to standard output.

Extra Credit

Complete the core language before attempting extra credit. Each option should include focused tests and a brief explanation in your README.

Reverse operator

Add unary ~, which reverses its operand. For example, ~"stressed" produces "desserts". It has the same precedence as unary !.

Conditional operator

Add the expression:

condition ? value_if_true : value_if_false

Only the selected value expression is evaluated. The operator is right-associative and binds less tightly than comparisons but more tightly than assignment. The empty string is false, exactly as it is for IF and WHILE.

CONTAINS is written as a keyword in the core language so that ? is available for this operator.

Replace operator

Add a string-replacement expression:

value | old_text -> new_text

It produces a copy of value in which every occurrence of old_text is replaced with new_text. Define and document sensible behavior when old_text is empty.
